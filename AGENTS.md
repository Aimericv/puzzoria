# Daily Grid architecture

- On explicit user instruction dated 2026-10-07, friend play uses private simultaneous live rooms for the nine catalogue games (`docs/DUELS.fr.md`). Reuse the solo adapters and server proofs with room ownership/start/deadline guards. Keep hidden answers/seeds and peer choices private, two seats maximum, common countdown, genuine opponent metrics, grace and mutual rematches. Opinion games reveal agreements rather than speed winners. Preserve old friend/number-room links; rareword stays Daily-only and its invitation creates classic Wordle. Live Practice results never enter Daily competition/community cohorts. Ranked and prizes remain future.

- Continue the existing adapters and preserve compatibility. On explicit owner instruction dated 2026-10-26, the autonomous agent may choose and develop new games or features from growth evidence and public trends without a separate product request. Prefer acquisition, SEO and retention experiments over cosmetic busywork. Authentication, payments, privacy/consent, authoritative server proofs, migrations, infrastructure and release-policy changes still require owner review. Automatic release eligibility is decided by the trusted supervisor, never by a model risk claim; production deployment stays off until the owner explicitly authorizes its first activation.
- Daily content is deterministic and published at 00:00 UTC. Preserve published IDs and answers. Practice uses fresh server-generated seeds and stable `/practice` routes; never generate indexable puzzle URLs.
- Active Daily games are Word, Unusual Word (`rareword`, available from 2026-10-04), Sudoku, Numbers and Minesweeper only (`src/lib/game-modes.ts`). 2048, Word Search, Blind Ranking, Guess the Number and Would You Rather open server-generated Practice on their indexable base game pages, without Daily controls. Their `/practice` aliases stay noindex. Preserve published puzzles through 2026-10-04 at historical archive URLs, but never create new Daily runs or publish later archive dates for these five games.
- Number duels use manual secret selection and manual higher/lower proposals, with empty inputs and no suggested values, calculated ranges or candidate grid. Fresh runs/rooms use `higher-lower` rules and `try` actions; preserve legacy `question`/`guess` proof replay and published answers. Keep number records and community cohorts separate by rules; mixed legacy/new games do not enter population comparisons.
- Unusual Word is a Wordle variant in the shared Word navigation, not a separate catalogue entry (`catalogGameIds`/`gameFamily`). Its stable URLs and internal `rareword` ID retain independent results/streaks. It reuses the Word adapter with 7–10 letters and 8/10 attempts and private editorial definitions released only after completion. Preserve the frozen initial deck and published IDs; Practice comparisons also require matching language, word length and attempt budget. See `content/rare-words/SOURCES.md`.
- Unusual Word offers one Daily word per locale, without new Practice runs from 2026-10-05. Its `/practice` alias permanently redirects to its Daily URL. Preserve owned legacy runs; after completion offer classic Wordle Practice with a fresh seed instead of another unusual word.
- All four word dictionaries are substantial. Preserve each locale's `legacyAnswers` and `answersFrom` when regenerating. `scripts/import-international-dictionaries.py` is a development-only import; runtime uses committed JSON. Keep dictionary source/license notices.
- Signup UI uses only unique username and password; the username becomes the initial display name. Preserve existing login identities when editing public names. Dedicated signup caps depend on a trusted overwritten proxy IP; never trust arbitrary forwarded headers.
- Account security uses credential generations (migration 6) and private authentication proofs to reject pending/stale logins after recovery, password change or logout-all. Password change verifies the current password, rotates this browser and revokes other sessions; logout-all verifies the password and revokes every session. Preserve recovery codes on normal password changes. A local common-password blocklist applies only to new passwords, never existing logins. See docs/SECURITY.fr.md.
- Personal data export and account deletion require fresh password verification; deletion also requires the login username. Erase associated rows atomically and preserve unrelated guest namespaces. Keep the private durable erasure journal on the backup volume and replay it before starting a restored container. Never allow public signup to claim a configured analytics-admin username, even after deletion. See docs/PREPRODUCTION.fr.md.
- Hints are currently disabled in both the game UI and public API. Keep the internal abstraction for future ads, but do not re-enable hints without user authorization.
- Advertising placeholders have been removed across the site. Do not reintroduce reserved ad space without a new user request. On explicit user instruction dated 2026-10-07, `COMMUNITY_STARTER_STATS=true` enables stable synthetic presentation comparisons below 20 compatible other account/device samples, without a label in the public UI. Observed cohorts replace them automatically. Never persist starter populations in results, votes, analytics or leaderboards. Keep the local finish-preview feature separate and disabled in production.
- `src/lib/server/` is private Node code. SQLite uses `DAILYGRID_DB_PATH`, defaults to ignored `.data/dailygrid.sqlite`, and requires Node 24.15+. Never expose database files, password hashes, owner cookies, or session tokens.
- Runs and results are authoritative on the server. Reuse `createRun`, `beginRun`, `submitRun`, `validateProof` and `migrateProgress`; do not trust browser score, time, user ID, success, eligibility or snapshots. The old challenge POST also requires an owned started run.
- Imported progress is personal, deduplicated, and excluded from leaderboards and population comparisons. Keep guest/account storage namespaces separate. Migration must remain retryable and never delete guest progress.
- Daily streaks and today's progress exclude Practice and historical Archive results. Preserve the first official result per owner/challenge, including across devices and languages for universal games.
- Do not show a target for completing all games today. Keep personal streaks and per-game progress.
- Comparisons require 20 distinct other account/device samples in a compatible cohort and 20 wins for winning time/attempt metrics, exclude assisted/recovered/implausibly fast games, and use strict slower-time counts for “faster than”. Never seed production with invented population data. The development-only loopback finish preview uses in-memory presentation fixtures; never persist them or enable the preview in production.
- All completed games reuse `CompletionPanel`: Replay/other game/invitation first, result sharing next to statistics, then comparisons and personal progress. Retain the board and scroll to the result. The local finish preview renders the owned puzzle with these same components; returning to the grid preserves its real draft, while Replay starts fresh Practice. Preview text sharing must be marked local and emit no result/share analytics. Word Search requires explicit Start before revealing the grid or starting its server timer. Avoid win rates for non-failable games and speed records for opinion games.
- Sudoku has one Daily grid at its level-free URL; three levels remain available in Practice. Preserve published levels through 2026-10-04 at archive URLs. From 2026-10-05 only easy is accepted for new Daily/archive Sudoku runs; retain that stable ID while hiding the Daily level selector. Base medium/hard URLs redirect permanently to the single Daily page.
- No-email recovery uses a random offline backup code, stored only as a hash in `account_recovery`. Display the raw code once, never persist it in browser storage or analytics. Consumption must atomically rotate the code, change the password and revoke all sessions. Existing accounts generate a code after verifying their current password.
- Leaderboards publish only display names of registered users and server-verified eligible Daily results. Win-rate rankings need 10 games in the selected UTC period. Use averages/current streaks rather than lifetime cumulative scores.
- Read `docs/RETENTION.md` before changing authentication, result storage, hints, analytics, or competition. Ranked, multiplayer and prize money are documented future boundaries, not active product features.
- Internal analytics combine authoritative server runs/results with optional first-party visit/action measurement (migration 5). Require explicit measurement choice; respect DNT/GPC, exclude admins/bots/local previews and never store inputs, secrets, full referrer URLs or client-supplied outcomes. The dashboard is behind existing-account login usernames in `ANALYTICS_ADMIN_USERNAMES`, default deny; expose aggregates only, never unique-human claims. Retention denominators require a fully elapsed UTC return day. Advertising telemetry stays disabled until an authorized provider integration; browser events never confirm revenue/rewards. See `docs/ANALYTICS.fr.md`.
- Public brand is Puzzoria (four locales, SVG assets). Preserve `dailygrid:*` persistence keys, authentication cookies, SQLite path and existing Docker volume/project names when editing branding; do not infer a purchased/public domain.
